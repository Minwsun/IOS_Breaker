# RevenueCat protocol review: `js/Crack.js`

Research date: 2026-10-21. This is a read-only protocol review of the repository script and public vendor sources. No production API was called, and no app credentials or customer data were accessed. This note describes the legacy handler. The new local implementation and its limits are documented in revenuecat-usage.md; neither has device verification.

## Findings

`/v1/product_entitlement_mapping` is a real RevenueCat SDK backend endpoint, not a generic entitlement-status endpoint. RevenueCat's current iOS SDK operation requests it as a GET. Its Swift response model exposes `productEntitlementMapping` with product properties `productIdentifier`, optional `basePlanId`, and `entitlements`; SDK tests prove the corresponding wire keys are snake_case (`product_entitlement_mapping`, `product_identifier`, `base_plan_id`, `entitlements`) ([SDK operation](https://raw.githubusercontent.com/RevenueCat/purchases-ios/main/Sources/Networking/Operations/GetProductEntitlementMappingOperation.swift), [response model](https://raw.githubusercontent.com/RevenueCat/purchases-ios/main/Sources/Networking/Responses/ProductEntitlementMappingResponse.swift), [fixture](https://raw.githubusercontent.com/RevenueCat/purchases-ios/main/Tests/UnitTests/Networking/Responses/Fixtures/ProductsEntitlements.json), [decoder tests](https://raw.githubusercontent.com/RevenueCat/purchases-ios/main/Tests/UnitTests/Networking/Responses/ProductEntitlementMappingDecodingTests.swift)). It describes the project's configured product-to-entitlement associations. It does not say which customer purchased which product, and therefore cannot establish anyone's active subscription by itself.

The earlier suspected schema mismatch is **not supported**. The current iOS SDK model and unit-test fixtures establish snake_case wire names, including `product_entitlement_mapping`, `product_identifier`, `base_plan_id`, and `entitlements`. `js/Crack.js:95, 98–99` therefore matches the published fixture schema. The current SDK test proves that its fixture decodes; it does not prove the live backend response across all versions. The script still fails to handle a base-plan-aware product key: its loop reads `product_identifier` but ignores the mapping key (which can be `product_identifier:base_plan_id`), a discrepancy relevant to accurate product modeling, not evidence of a parsing failure.

The loop's destructured `entitlementId` at `js/Crack.js:97` is actually a product-map key under the current SDK model and is never used. The script uses the mapped entitlement list to construct a fabricated subscriber record (`js/Crack.js:77–93, 101–129`), with generated purchase/expiry dates and transaction identifiers (`js/Crack.js:17–59, 101–104`), then replaces the original body (`js/Crack.js:132–133`). The endpoint does not supply that user-specific purchase evidence. The constructed object is thus not a transformation of valid customer purchase state.

`js/Crack.js:71–74` ignores the transport error and HTTP status, parses `data` without guarding empty/non-JSON bodies, and assumes the mapping fields exist. Network failures, rate limits, auth errors, or a schema change can throw before `$done` is called, leaving the proxy handler unresolved. Separately, `js/Crack.js:75, 90` generates an unrelated new `original_app_user_id`, rather than preserving the subscriber identity returned by RevenueCat; this breaks identity continuity and makes the payload internally inconsistent with a real customer. Any client-side replacement remains distinct from an App Store purchase.

## Wire-format and signature verification cross-check

The published [RevenueCat iOS mapping response fixture](https://raw.githubusercontent.com/RevenueCat/purchases-ios/main/Tests/UnitTests/Networking/Responses/Fixtures/ProductsEntitlements.json) uses snake_case keys and is exercised by [ProductEntitlementMappingDecodingTests](https://raw.githubusercontent.com/RevenueCat/purchases-ios/main/Tests/UnitTests/Networking/Responses/ProductEntitlementMappingDecodingTests.swift). The model's explicit `CodingKeys` plus those fixture/assertions resolve the camelCase-vs-snake_case question; Swift property names alone were insufficient to infer wire keys. A second fixture documents `base_plan_id` and compound product keys such as `com.revenuecat.foo_1:monthly` ([fixture](https://raw.githubusercontent.com/RevenueCat/purchases-ios/main/Tests/UnitTests/Networking/Responses/Fixtures/ProductsEntitlementsWithBasePlanId.json)).

In the iOS SDK, signature verification uses a nonce on supported requests (`X-Nonce`), and may send `X-Headers-Hash` for signed request headers; the response signature arrives as `X-Signature`, with response time in `X-RevenueCat-Request-Time` (see [HTTPRequest](https://raw.githubusercontent.com/RevenueCat/purchases-ios/main/Sources/Networking/HTTPClient/HTTPRequest.swift), [HTTPClient header definitions](https://raw.githubusercontent.com/RevenueCat/purchases-ios/main/Sources/Networking/HTTPClient/HTTPClient.swift), [response verification](https://raw.githubusercontent.com/RevenueCat/purchases-ios/main/Sources/Security/Signing+ResponseVerification.swift)). `X-Signature` is a **response** header, not the request header. The SDK request snapshot for signature-enabled tests shows `X-Nonce` and `X-Headers-Hash` ([snapshot](https://raw.githubusercontent.com/RevenueCat/purchases-ios/main/Tests/UnitTests/Networking/Backend/__Snapshots__/BackendSignatureVerificationTests/iOS17-testRequestContainsSignatureHeader.1.json)); its Authorization value in such test snapshots is fixture data and must not be treated as a real credential. Exact headers depend on SDK version, endpoint support, and verification configuration.

## Authentication and response integrity

RevenueCat documents public API keys as the keys intended to configure its SDK and describes secret keys as server-only, high-impact credentials. The SDK's key is not proof that the caller owns a paid entitlement ([API keys](https://www.revenuecat.com/docs/projects/authentication), [API v1 overview](https://www.revenuecat.com/docs/api-v1)). Copying an intercepted `Authorization` header into a second request, as `js/Crack.js:62–68` does, makes the handler depend on whichever request happened to be intercepted and replays that header to the configured RevenueCat host. Public SDK keys are designed for client use; this does not make them entitlement proof. Avoid collecting or logging credentials, and revoke/rotate a secret key if one is exposed.

RevenueCat's Trusted Entitlements feature verifies cryptographic signatures over entitlement responses. The SDK obtains the signature material and validates the response; its `EntitlementInfo`/`EntitlementInfos` expose verification results such as `verified`, `verifiedOnDevice`, `failed`, and `notRequested`. RevenueCat explicitly warns that enabling informational verification alone does not block access: the app must enforce its policy ([Trusted Entitlements docs](https://www.revenuecat.com/docs/customers/trusted-entitlements)). Thus a body-replacement proxy can be detected by a properly configured app, but behavior depends on the app's SDK version, verification mode, and app-side handling. Do not claim all RevenueCat apps reject modified bodies or all accept them.

The SDK source models customer info separately from product mapping. Its current response requires a `subscriber`, `requestDate`, and fields such as `originalAppUserId`, subscriptions, non-subscriptions, and entitlements ([CustomerInfo response model](https://raw.githubusercontent.com/RevenueCat/purchases-ios/main/Sources/Networking/Responses/CustomerInfoResponse.swift)). This confirms that a mapping is not interchangeable with `CustomerInfo`; optional/default fields and accepted raw data are handled by SDK decoding, not by a generic hand-built object.

## Other subscription platforms

There is no safe generic “Pro” response format that can cover other subscription vendors. Qonversion's official SDK says its backend validates store purchases and the SDK checks Qonversion entitlements; it uses its own project key, user identities, APIs, and entitlement model ([iOS SDK](https://github.com/qonversion/qonversion-ios-sdk), [Android SDK](https://github.com/qonversion/android-sdk)). Adapty documents profile objects and paid access levels with its own schema and APIs ([official API object reference](https://github.com/adaptyteam/adapty-docs/blob/main/src/content/docs/version-3.0/server-side-api-objects.mdx)). These are separate integrations; RevenueCat headers or payloads do not establish their status. Glassfy announced service shutdown in December 2024 and its migration process required replacing its SDK and moving data ([Adapty migration notice](https://adapty.io/blog/migrate-from-glassfy-to-adapty/)); it is not a current generic API candidate.

## Defensive maintenance and validation

The new `js/revenuecat-compatible.js` preserves original customer identity and unrelated fields, looks up product mapping on the same RevenueCat host, and passes through signed responses and transport/parse errors. It skips Android base-plan records. It changes client-visible entitlement dates; this does not establish a server purchase or generate a valid response signature. See [usage and limitations](revenuecat-usage.md).

Offline fixture tests cover snake_case and camelCase parsing, callback completion, identity preservation, routing, selector boundaries, timeout, malformed inputs and signed-response pass-through. No live API or device integration test was run. The SDK fixtures establish the raw snake_case format; camelCase is an additional adapter format, not evidence of wire-schema drift.
