# Premium-app mapping: evidence and freshness

**Reviewed:** 2026-10-21. **Scope:** read-only review of `js/revenuecat.js`, this checkout’s Git history, the credited public GitHub sources, RevenueCat documentation and current App Store listings. No app API, account, receipt, or subscription service was called. This note separates public script evidence from compatibility actually verified on a device.

## Finding

The repository contains a broad, hand-maintained set of app-name-to-entitlement labels, but the checked-in file does not establish which mappings work today. At [js/revenuecat.js:10–15](../js/revenuecat.js#L10), the interception rule targets RevenueCat receipt/subscriber response routes on `api.revenuecat.com` generically; it does not define a 1Blocker- or Endel-specific endpoint. The visible response code at [lines 333–379](../js/revenuecat.js#L333) parses a generic RevenueCat customer object and modifies it after choosing a mapping from the request User-Agent. The implementation is obfuscated, so this code is not evidence that Apple or RevenueCat accepted a purchase or that the app trusts that response. There are no app-version-specific fixtures, captured real responses, automated mapping tests, or official entitlement-ID references in the repo. Consequently “the app sells Premium today” is not evidence that its RevenueCat project uses the string listed here, or that a modified response grants a feature.

The public RevenueCat docs describe the service and its general customer/receipt resources, but app-specific entitlement identifiers and product-to-entitlement links are configured per developer project. They are not discoverable from an app’s store listing. Do not infer an app’s schema from a generic RevenueCat endpoint or from labels like `premium`, `pro`, `Gold`, or `membership`. [RevenueCat API v1 overview](https://www.revenuecat.com/docs/api-v1), [RevenueCat iOS SDK](https://github.com/RevenueCat/purchases-ios).

## 1Blocker: VPN interaction matters separately from subscription state

The [official VPN compatibility article](https://support.1blocker.com/en/articles/9313600-in-app-tracking-filter-vpns) explains that its in-app tracking filter installs a local VPN and normally conflicts with other active VPN profiles. Some IKEv2/IPsec Personal VPN configurations may coexist in DNS Proxy mode; compatibility is not guaranteed. This can stop a Shadowrocket interception session even if a subscription script itself has no JavaScript error. Safari content-blocking extensions are a separate mechanism. A VPN badge or successful filter activation alone does not establish paid entitlement access.
